## Решения

### Архитектура

Сохранил существующую структуру проекта, добавив несколько небольших директорий с разделением ответственности.

- `types/match.ts` — описание типов данных.
- `api/matches.ts` — выполнение HTTP-запроса.
- `api/matches.validation.ts` — проверка структуры ответа сервера.
- `hooks/useMatches.ts` — управление загрузкой данных, ошибками и обновлением.
- `hooks/useFavorites.ts` — управление избранными матчами.
- `utils/matches.ts` — фильтрация, перевод статусов и форматирование дат.
- `components/MatchCard.tsx` — отображение отдельного матча.
- `screens/MatchesScreen.tsx` — основной экран со списком и фильтрами.

Старался не перегружать экран бизнес-логикой и не добавлять лишние зависимости. Для HTTP-запросов использовал стандартный `fetch`, а для управления состоянием — React-хуки.

### Валидация ответа API

Данные, полученные с сервера, имеют тип `unknown` до проверки их структуры.

Реализовал простую проверку ответа, включая вложенные объекты команд и счёта. Если данные не соответствуют ожидаемому контракту, выбрасывается ошибка, которая обрабатывается в хуке загрузки.

Это позволяет не использовать небезопасное приведение через `as MatchesResponse` без предварительной проверки.

### Фильтрация матчей

Распределил матчи по следующим правилам:

- `scheduled` — «Предстоящие».
- `postponed` — «Предстоящие».
- `finished` — «Завершённые».
- `live` — только «Все».
- Неизвестные статусы — только «Все».

Перенесённые матчи отношу к предстоящим, поскольку они ещё не сыграны. Матчи `live` не считаю ни предстоящими, ни завершёнными, так как они уже начались, но ещё не закончились.

Неизвестные статусы не исключаю из общего списка, чтобы новые значения от API не приводили к потере матчей.

### Неочевидные случаи в данных

**1. Нулевой счёт**

В данных присутствует результат `0:0`. При отображении использовал оператор `??`, а не `||`, чтобы значение `0` не воспринималось как отсутствие счёта.

**2. Отсутствующий счёт**

Поле `score` может содержать `null`. В таком случае вместо результата отображается прочерк.

**3. Отсутствующая дата**

У перенесённого матча `startsAt` может быть `null`. Вместо некорректной даты отображается «Дата уточняется».

Дополнительно предусмотрена обработка строк с некорректной датой.

**4. Необязательное поле minute**

Поле `minute` присутствует не у всех матчей. Для статуса `live` отображается текущая минута, если она передана сервером.

**5. Часовой пояс**

Время матчей приходит в стандартном формате с указанием UTC.

Для отображения использовал `Intl.DateTimeFormat` с локалью `ru-RU`, не задавая `timeZone` вручную. Благодаря этому время автоматически преобразуется в часовой пояс устройства.

**6. Несоответствие статуса текущей дате**

В тестовых данных встречаются матчи со статусом `scheduled`, дата которых уже прошла.

Поэтому статус определяется исключительно по полю `status`, а не путём сравнения времени матча с текущей датой.

**7. Пустой ответ**

Пустой массив `matches` считаю корректным ответом сервера. Для него реализовано отдельное состояние интерфейса с сообщением об отсутствии матчей.

### Обновление данных

Для повторной загрузки реализована кнопка «Обновить».

Время последнего обновления сохраняется только после успешного HTTP-запроса. При ошибке предыдущие данные остаются доступными пользователю.

Для отмены запросов используется `AbortController`. Это позволяет избежать обновления состояния после размонтирования компонента и уменьшает риск обработки устаревших ответов.

### Интерфейс

Использовал стандартные компоненты React Native, совместимые с Expo Web, iOS и Android.

Для десктопной версии ограничил максимальную ширину контента, а для мобильных экранов предусмотрел перенос элементов и адаптивные отступы.

Статусы выделены цветами:
- Зелёный — завершённый матч.
- Синий — предстоящий.
- Жёлтый — перенесённый матч или неизвестная дата.
- Красный — матч в процессе.
- Серый — неизвестный статус.

Звёздочка избранного расположена в правом верхнем углу карточки и использует основной синий цвет интерфейса.

## Баги из части 2

### 1. Звёздочки

**Почему происходило:**

В `useFavorites` использовалось выражение `Boolean(favorites.indexOf(id))`. Если элемент отсутствует, `indexOf` возвращает `-1`, которое преобразуется в `true`. При этом индекс `0` преобразуется в `false`, поэтому состояние избранного определялось неправильно.

Дополнительно массив `favorites` изменялся напрямую через `push` и `splice`, после чего передавался в `setFavorites` по той же ссылке. React мог не увидеть изменение состояния и пропустить повторный рендер.

**Что исправил:**

Заменил `indexOf` на `includes` и реализовал иммутабельное обновление массива через функциональный `setFavorites`, `filter` и spread-оператор.

Подключил `FavoriteButton` к карточкам и добавил `extraData={favorites}` в `FlatList`, чтобы список учитывал изменения избранного.

### 2. «Обновлено N сек назад»

**Почему происходило:**

В исходном `UpdatedAgo` функция внутри `setInterval` использовала значение `seconds` из первого рендера из-за замыкания (stale closure). В результате счётчик постоянно пытался установить одно и то же значение.

Кроме того, интервал не очищался при размонтировании, а изменение `since` не запускало новый отсчёт.

**Что исправил:**

Вместо увеличения сохранённого счётчика вычисляю фактически прошедшее время через разницу между `Date.now()` и `since`.

Добавил зависимость от `since` в `useEffect`, пересчёт времени при его изменении и очистку интервала через `clearInterval`.

## Как я использовал ИИ

Использовал ChatGPT для анализа задания, изучения существующего кода, обсуждения архитектуры и подготовки отдельных частей реализации.

Не переносил решения без разбора: изучал предложенный код, уточнял назначение функций и корректировал решения под требования проекта.

**Случаи, когда предложения ИИ пришлось пересмотреть:**

**1. Валидация API**

Первоначально ИИ предложил упрощённую проверку ответа, которая проверяла только `round` и наличие массива `matches`.

Такой подход не гарантировал корректность вложенных данных: команд, счёта и остальных полей.

В итоге выбрал отдельный модуль валидации с TypeScript type guards, который проверяет структуру каждого матча.

**2. Использование Zod**

ИИ предложил библиотеку Zod для проверки данных во время выполнения.

Для небольшого тестового проекта дополнительная зависимость показалась избыточной. Решил реализовать проверку самостоятельно, сохранив разделение типов, валидации и HTTP-запросов.

**3. Расположение кнопки избранного**

При изменении расположения звёздочки ИИ предложил абсолютное позиционирование с дополнительным отступом, из-за которого сместился счёт одной из команд.

Проблему обнаружил при визуальной проверке в браузере. Самостоятельно скорректировал отступы карточки, чтобы звёздочка не нарушала расположение счёта.

**Проверка результата**

Проверял работу приложения в браузере и устройствах на iOS/Android: загрузку матчей, фильтрацию, отображение счёта и статусов, работу избранного и обновление данных.

Отдельное внимание уделил пограничным случаям из `matches.json`, причинам ошибок в чужом коде и корректности обновления React-состояния.
